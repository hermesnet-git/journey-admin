Sumário

Como o ms-journey entrega a tela

Quando a instância está numa tarefa de usuário, o ms-journey lê no motor a tarefa aberta e as variáveis da instância e pede a tela daquele nó ao ms-espec-registry. É lá que a tela publicada recebe os valores: placeholders, vínculos, fontes de dados e listas. O ms-journey devolve o resultado ao canal sem alterar nada. Os cinco exemplos mostram, para cada recurso, o que entra e o que sai; em seguida, cinco diagramas de sequência mostram a conversa entre ms-journey, ms-espec-registry e ms-runtime-camunda, e a página fecha com uma melhoria proposta: o estado das tarefas assíncronas em Redis.

1 · TarefaGET /task?processInstanceIdnó da tela aberta
2 · VariáveisGET /process-instance/{id}/variablesform_*, data_*, channel
3 · TelaPOST …/nodes/{nodeId}/form/resolveversão da instância + variáveis
4 · Entregastep.form.sduirepassado ao canal sem alteração

Nos exemplos, âmbar marca o que o servidor consome (some ou é substituído) e verde marca o valor que chega resolvido. Variáveis aparecem com o nome que têm no motor: form.plano na tela é form_plano no motor.

1. Placeholders de texto

Qualquer atributo de texto pode ter {{…}}. O servidor troca cada placeholder pelo valor da variável antes de entregar a tela.

Tela publicada
["ui.screen", { "id": "s", "version": "1.0.0",
  "title": "Olá, {{data.nomeCliente}}" }, [
  ["ui.text", { "id": "t1", "version": "1.0.0",
    "text": "Plano: {{form.plano}} · canal {{channel}}" }],
  ["ui.text", { "id": "t2", "version": "1.0.0",
    "text": "Protocolo: {{data.protocolo}}" }]
]]
Variáveis da instância
data_nomeCliente  "Ana"            String
form_plano        "Controle 20GB"  String
channel           "WEB"            String
data_cpf          "12345678900"    String

(data_protocolo não existe)
ms-journey → form/resolve → entregue ao canal
"sdui": { …, "data": ["ui.screen", { "id": "s", "version": "1.0.0",
  "title": "Olá, Ana" }, [
  ["ui.text", { "id": "t1", "version": "1.0.0", "text": "Plano: Controle 20GB · canal WEB" }],
  ["ui.text", { "id": "t2", "version": "1.0.0", "text": "Protocolo: " }]

"context": {
  "form": { "data_nomeCliente": "Ana", "form_plano": "Controle 20GB", "channel": "WEB" },
  "data": { "data_nomeCliente": "Ana", "form_plano": "Controle 20GB", "channel": "WEB" }
}
  • Formas aceitas: {{form.x}}, {{data.x}}, o nome no motor ({{form_x}}, {{data_x}}) e {{channel}}. Qualquer outra forma vira texto vazio, e a publicação já recusa.
  • Variável inexistente vira texto vazio, nunca o {{…}} literal.
  • Vale para todo atributo de texto cujo nome não começa com $. Parâmetros de $events não são interpolados.
  • O context leva só as variáveis que a tela referencia: data_cpf ficou de fora. form e data trazem o mesmo mapa.

Código: TemplateResolver.resolveTemplate, BindingResolver.engineVariableNameOfPlaceholder, CanonicalFormat.referencedProcessVariables.

2. Vínculos e condições

Um vínculo em $bindings grava o valor da variável no atributo de mesmo nome. Condições ($visibility, $active) seguem intactas para o canal avaliar.

Tela publicada
["ui.textInput", { "id": "email", "version": "1.0.0", "label": "E-mail",
  "$bindings": { "value": { "path": "form.email", "mode": "twoWay" } } }],
["ui.text", { "id": "saldo", "version": "1.0.0", "text": "—",
  "$bindings": { "text": { "path": "data.saldo", "mode": "oneWay" } } }],
["ui.textInput", { "id": "tel", "version": "1.0.0", "label": "Celular",
  "$bindings": { "value": { "path": "form.telefone", "mode": "twoWay" } } }],
["ui.alert", { "id": "aviso", "version": "1.0.0",
  "severity": "warning", "message": "Saldo baixo",
  "$visibility": { "rule": "equals", "path": "data.saldoBaixo", "value": true } }]
Variáveis da instância
form_email       "ana@exemplo.com"  String
data_saldo       42.5               Double
data_saldoBaixo  true               Boolean

  "$bindings": { "value": { "path": "form.email", "mode": "twoWay" } },
  "value": "ana@exemplo.com" }],
["ui.text", { "id": "saldo", "version": "1.0.0", "text": 42.5,
  "$bindings": { "text": { "path": "data.saldo", "mode": "oneWay" } } }],
["ui.textInput", { "id": "tel", "version": "1.0.0", "label": "Celular",
  "$bindings": { "value": { "path": "form.telefone", "mode": "twoWay" } } }],
["ui.alert", { "id": "aviso", "version": "1.0.0",
  "severity": "warning", "message": "Saldo baixo",
  "$visibility": { "rule": "equals", "path": "data.saldoBaixo", "value": true } }]

"context": { "form": { "form_email": "ana@exemplo.com", "data_saldo": 42.5, "data_saldoBaixo": true }, "data": { … } }
  • A chave do vínculo é o atributo que recebe o valor: value num campo, text num texto. O valor sai com o tipo da variável (42.5 é número, não texto).
  • oneWay e twoWay são resolvidos do mesmo jeito: um campo revisitado já chega preenchido. A diferença fica com o canal, que só devolve nas respostas os campos twoWay em form.*.
  • Sem variável, o atributo não é criado e o campo nasce vazio (tel).
  • $bindings, $events, $visibility e $active não são removidos. A variável da condição entra no context (data_saldoBaixo) para o canal reavaliar enquanto a pessoa preenche.

Código: TemplateResolver.resolveAttributes, BindingResolver.resolve.

3. Fonte de dados num select

A tela pode declarar fontes de dados. O ms-espec-registry as chama a cada montagem da tela e entrega as opções prontas; a configuração da fonte nunca chega ao canal.

Tela publicada (envelope)
"dataSources": {
  "ufs": {
    "source": "Catálogo de UFs",
    "url": "https://api.exemplo/ufs?cliente={cpf}",
    "params": { "cpf": "{{data.cpf}}" },
    "itemsPath": "$.itens",
    "exposedFields": ["label", "value"],
    "timeoutMs": 3000,
    "required": true
  }
},
"data": ["ui.screen", { … }, [
  ["ui.select", { "id": "uf", "version": "1.0.0", "label": "Estado",
    "$bindings": {
      "options": { "path": "data.ufs", "mode": "oneWay" },
      "value": { "path": "form.uf", "mode": "twoWay" } } }]
]]
Variáveis e chamada à fonte
data_cpf  "12345678900"  String

"dataSources": {},
"data": ["ui.screen", { … }, [
  ["ui.select", { "id": "uf", "version": "1.0.0", "label": "Estado",
    "$bindings": { "value": { "path": "form.uf", "mode": "twoWay" } },

  • Cada {nome} da URL é trocado pelo parâmetro de mesmo nome, já interpolado e codificado ({{data.cpf}} → 12345678900).
  • itemsPath aponta a lista na resposta ($ ou $.a.b); só os exposedFields passam (ibge foi descartado). No select, só entram itens com label e value.
  • O resultado vale só para esta montagem: aparece no context como data_<apelido> e nunca vira variável da instância. O vínculo options sai de $bindings.
  • As fontes são chamadas em sequência, com conexão de 3 s e o timeoutMs da fonte (padrão 5 s). Cada chamada grava uma linha em espec_registry.data_source_call.

Código: ScreenDataSourceFetcher.fetchAll, ListMaterializer.selectOptions, ResolveScreenForNode.resolveEnvelope.

4. Lista de seleção

ui.selectList é montada inteira no servidor: cada item vira value, title e description, e as regras que liberam cada ação são avaliadas item a item.

5. Fonte de dados que falhou

Se a fonte não responde, responde fora de 2xx ou devolve algo ilegível, a tela é entregue mesmo assim: a lista vem vazia e o componente recebe loadError.

Tela publicada
"dataSources": {
  "ufs": { "url": "https://api.exemplo/ufs?cliente={cpf}",
           "params": { "cpf": "{{data.cpf}}" },
           "timeoutMs": 3000, "required": true,
           "errorMessage": "Não foi possível carregar os estados agora." }
},
"data": ["ui.screen", { … }, [
  ["ui.select", { "id": "uf", "version": "1.0.0", "label": "Estado",
    "$bindings": { "options": { "path": "data.ufs", "mode": "oneWay" },
                   "value": { "path": "form.uf", "mode": "twoWay" } } }],
  ["ui.button", { "id": "retry", "version": "1.0.0", "label": "Tentar novamente",
    "$events": { "onPress": { "action": "action.retry" } } }]
]]
Chamada à fonte
GET https://api.exemplo/ufs?cliente=12345678900

... sem resposta em 3000 ms

  duration_ms  3001
  error        A fonte não respondeu em até 3000 ms

["ui.select", { "id": "uf", "version": "1.0.0", "label": "Estado",
  "$bindings": { "value": { "path": "form.uf", "mode": "twoWay" } },

  "loadError": { "message": "Não foi possível carregar os estados agora.", "required": true } }],

  "$events": { "onPress": { "action": "action.retry" } } }]
  • A mensagem vem de errorMessage da fonte; sem ela, “Não foi possível carregar as informações agora.”.
  • required: true diz ao canal que a etapa não pode ser enviada enquanto a fonte não carregar.
  • action.retry é só um novo GET /instances/{id}/current-step: o ms-journey refaz os passos 1 a 4 e a fonte é chamada de novo.
  • A falha não vira erro HTTP nem toca a instância: o motor não sabe que a fonte falhou.

Código: ScreenDataSourceFetcher.fetch, ListMaterializer.putLoadError.

Tudo isso roda em ResolveScreenForNode.execute (ms-espec-registry), a cada current-step, início, envio ou voltar que caia numa tarefa de usuário. O ms-journey só encaminha: o sdui chega a ele como objeto opaco (FormPayload) e segue igual para o canal.

6. Sequência · Iniciar a jornada

O canal cria a instância. O ms-espec-registry valida e tipa as variáveis de entrada, o motor executa até a primeira espera e o ms-journey resolve essa primeira etapa antes de responder.

Variáveis declaradas no Início são obrigatórias; as extras também entram, como data_<nome>. Código: JourneyController.start, VariableConversion.fromDeclaredVariables.

7. Sequência · Etapa atual numa tela

É a sequência que todas as outras reaproveitam (JourneyStepResolver.resolve): quatro leituras no motor e uma chamada ao ms-espec-registry, que monta a tela como nos exemplos 1 a 5.

Com variável do tipo Json (listas), há uma leitura extra de /variables?deserializeValues=false. Nada é guardado entre chamadas: cada consulta refaz tudo.

8. Sequência · Concluir a tela e avançar

O envio confere se a tarefa ainda é a aberta, converte as respostas pela tela publicada e conclui no motor. A resposta já é a próxima etapa; se uma integração síncrona falhar, o motor desfaz tudo e a mesma tela volta com a mensagem.

O resolve inicial monta a tela atual inteira (inclusive fontes de dados) só para validar o taskId. Código: JourneyController.completeTask, VariableConversion.fromAnswers.

9. Sequência · Tarefa assíncrona e espera

Quando o fluxo envia para o Kafka e aguarda a resposta, o motor para numa tarefa externa e depois numa espera de mensagem. O ms-journey só enxerga WAITING, e o canal descobre que acabou consultando de novo.

Entre o fim da espera e a próxima consulta, o canal não sabe de nada; e WAITING não diz se o envio está pendente, foi feito, falhou ou se a resposta ainda não chegou. É o que a melhoria da seção 11 resolve. Código: KafkaConnectorWorker (@Scheduled(fixedDelay = 3000), correlate).

10. Sequência · Voltar à tela anterior

O Voltar decide pelo histórico do motor qual tela reabrir e recusa se houver uma integração de escrita concluída entre as duas telas.

O fluxo consultado é o da publicação atual, não o da versão da instância. Código: JourneyController.back, BackNavigation.decide, CamundaEngineClient.reopenActivity.

11. Melhoria proposta · Estado assíncrono em Redis

Novo · proposta

O ms-runtime-camunda passa a publicar num Redis exclusivo da plataforma o estado de cada instância e de cada tarefa assíncrona, sempre depois que a transação do motor é confirmada. O ms-journey lê o Redis primeiro: em espera, responde sem tocar o motor. O estado de cada tarefa assíncrona fica dentro da plataforma, para o Diagnóstico e o monitoramento. O motor continua sendo a fonte da verdade.

O problema hoje

  • Só polling. Em WAITING, o canal consulta de novo sem saber quando vale a pena (sequência 9).
  • Polling caro. Cada consulta em espera faz 4 chamadas ao motor (instância, versão, tarefas, atividade atual) e 1 ao ms-espec-registry.
  • Sem visibilidade. WAITING traz só nome e tipo do nó. Não diz se o envio ao Kafka está na fila, em tentativa, concluído ou falhou, nem se a resposta esperada já chegou.

Como fica a sequência

Em verde, o que é novo. A tela continua sendo montada na hora (depende das variáveis e das fontes de dados); o Redis guarda só o estado.

Estados de uma tarefa assíncrona

Cada transição corresponde a um ponto que já existe no ms-runtime-camunda (tabela abaixo). FAILED_HANDLED segue pela saída “Se falhar”; INCIDENT e TIMED_OUT sem saída desenhada param a instância.

Os eventos do motor (tarefa criada, atividade iniciada, temporizador, fim) cabem num único HistoryEventHandler registrado por ProcessEnginePlugin, ao lado do handler padrão. As tentativas e o erro de envio saem do próprio KafkaConnectorWorker.

Regras do desenho

  • Gravar só depois do commit. A escrita é registrada com addTransactionListener(TransactionState.COMMITTED, …). Assim, um rollback (sequência 8) nunca aparece no Redis.
  • Redis é cache, o motor é a verdade. Chave ausente ou Redis fora do ar: o ms-journey faz o resolve completo de hoje. Como as chaves são apagadas no fim, uma instância encerrada cai nesse caminho e o motor responde ENDED. Uma espera de mais de 24 h sem nenhum evento também cai nele até o motor gravar de novo, na retomada. Nada quebra sem o Redis.
  • Ordem garantida pelo rev. Worker e executor de jobs escrevem em threads diferentes; um script Lua só aplica a escrita se o updatedAt do evento for mais novo que o gravado.
  • O canal continua no polling. Nada muda nas rotas: o canal consulta current-step como hoje, mas a consulta em espera passa a custar uma leitura no Redis em vez de 4 chamadas ao motor e 1 ao ms-espec-registry.
  • O detalhe fica na plataforma. O canal continua recebendo só WAITING, com nome e tipo do nó; o contrato não muda. O estado das tarefas assíncronas (kind, status, attempts, error) serve ao Diagnóstico do admin e ao monitoramento.

Decisões

TemaDecisão
RedisDecidido Exclusivo da plataforma.
Como o canal acompanha a esperaDecidido Só polling em current-step; sem long-polling, SSE ou Pub/Sub.
Versão da definiçãoDecidido Cache de versionTag por definitionId, sem expiração.
Detalhe da tarefa assíncronaDecidido Só dentro da plataforma (Diagnóstico e monitoramento). O canal recebe só WAITING, como hoje.
