ms-journey · API v1

API de canais do Elastic Journey

O ms-journey é a única porta de entrada de um canal digital para executar jornadas publicadas no Elastic Journey. O canal inicia a jornada, recebe a etapa atual, desenha a tela que vem descrita na resposta e devolve o que a pessoa preencheu. Fluxo, decisões, integrações e montagem das telas ficam na plataforma.

Endereço local
http://localhost:8085/api/v1
Formato
JSON, content-type: application/json
Autenticação
Em definição. Hoje o serviço não exige credencial: exponha-o só por trás do BFF do canal.
Etapas
USER_TASK (tela), WAITING (espera) e ENDED (fim)

As seis operações

OperaçãoRotaEnviaRecebe
Fluxo da jornadaGET /journeys/{journeyId}/flow—{ channelTypes, flowNodes }
IniciarPOST /journeys/{journeyId}/instances?channelType=…variáveis de entradainstância e primeira etapa
Etapa atualGET /instances/{processInstanceId}/current-step—etapa
Concluir a telaPOST /instances/{processInstanceId}/tasks/{taskId}/complete{ "answers": { … } }próxima etapa
VoltarPOST /instances/{processInstanceId}/back—etapa anterior, ou a mesma com errorMessage
EncerrarDELETE /instances/{processInstanceId}—200 sem corpo
Ciclo mínimo
# 1. Iniciar: a resposta já traz a primeira etapa
curl -X POST "http://localhost:8085/api/v1/journeys/{journeyId}/instances?channelType=WEB" \
  -H "content-type: application/json" \
  -d '{ "cpf": "12345678900", "nomeCliente": "Ana Souza" }'

# 2. Enviar a tela recebida: a resposta é a próxima etapa
curl -X POST "http://localhost:8085/api/v1/instances/{processInstanceId}/tasks/{taskId}/complete" \
  -H "content-type: application/json" \
  -d '{ "answers": { "email": "ana.souza@exemplo.com", "aceite": true } }'

# 3. Em espera, consultar de novo
curl "http://localhost:8085/api/v1/instances/{processInstanceId}/current-step"

Arquitetura

O canal conversa só com o ms-journey. O ms-journey não tem banco: a cada pedido, junta o que o motor diz sobre a instância com o que o ms-espec-registry diz sobre a jornada publicada, e devolve uma resposta pronta.

  • ms-journey resolve a etapa, valida o envio de cada tela e repassa a tela SDUI sem alterá-la.
  • ms-espec-registry é dono das telas publicadas e das conversões de tipo. Lê as versões no Postgres do admin e guarda as telas publicadas e o registro das consultas às fontes de dados no schema espec_registry.
  • ms-runtime-camunda executa o fluxo: decisões, integrações REST (síncronas ou em segundo plano), envio e recebimento de mensagens Kafka e temporizadores. Depois de cada commit, grava no Redis o estado da instância.
  • Redis, exclusivo da plataforma, guarda o estado de cada instância (24 h, renovado a cada escrita, apagado no fim), o detalhe das tarefas assíncronas e a versão de cada definição. É ele que permite responder uma etapa em espera sem chamar o motor.

Ciclo de uma etapa

Toda chamada que muda a instância roda uma transação no motor, que termina numa tela, numa espera ou no fim. O canal só enxerga esses três estados.

GET/journeys/{journeyId}/flow

Fluxo da jornada

Devolve o fluxo publicado, recortado para o canal. Use para saber quais canais a jornada atende e quais variáveis de entrada o início exige (nó com type igual a START).

CampoDescrição
channelTypesCanais que a jornada atende: WEB, MOBILE, WHATSAPP.
flowNodes[].idId do nó, o mesmo que aparece em nodeId das etapas.
flowNodes[].typeSTART, MESSAGE_START_EVENT, USER_TASK, SERVICE_TASK, RECEIVE_TASK, GATEWAY, END.
flowNodes[].nameNome do nó.
flowNodes[].startVariablesNo START: { name, type } de cada variável de entrada. Tipos: string, number, boolean, date, datetime.

POST/journeys/{journeyId}/instances?channelType={canal}

Iniciar uma jornada

Cria a instância e devolve a primeira etapa já resolvida. O canal começa a desenhar sem outra chamada.

ParâmetroOndeDescrição
journeyIdrotaUUID da jornada publicada.
channelTypequeryWEB, MOBILE ou WHATSAPP. Vira a variável channel. O serviço não confere contra flow.channelTypes: use um canal que a jornada atende.
corpoJSONVariáveis de entrada: { "cpf": "…", … }. Todas as declaradas no Início são obrigatórias; extras também entram.

O que acontece

  1. O ms-espec-registry valida e tipa as variáveis de entrada pela publicação atual. Elas viram data_<nome>.
  2. O ms-journey acrescenta channel e um businessKey (UUID) e inicia no motor a versão mais recente implantada.
  3. O motor executa decisões e integrações síncronas até a primeira espera e, depois do commit, grava o estado no Redis.
  4. O ms-journey resolve a primeira etapa pelo motor e busca o fluxo publicado.

Resposta

CampoDescrição
processInstanceIdIdentificador da instância, usado em todas as chamadas seguintes. Guarde-o: é ele que retoma a jornada.
businessKeyIdentificador de negócio gerado pelo serviço (UUID). Sistemas externos podem usá-lo como correlationId de mensagens.
flowO mesmo conteúdo de GET /journeys/{journeyId}/flow.
stepA primeira etapa, já resolvida.

  1. 1
    POST /journeys/{jid}/instances?channelType=WEB

    O canal envia as variáveis de entrada no corpo e informa o canal na query.

  2. 2
    POST /journeys/{jid}/start-variables/convert

    O ms-journey pede ao ms-espec-registry para validar e tipar as variáveis de entrada.

  3. 3
    journey_publication · nó START

    O registro lê a publicação atual, confere se a jornada não termina só com integrações síncronas (senão, 502) e aplica os tipos declarados no Início.

  4. 4
    { data_cpf, data_nomeCliente } tipadas

    Toda variável declarada é obrigatória: faltando alguma, a resposta é 409 e nada é criado. Chaves extras também entram, como data_.

  5. 5
    + channel = WEB · businessKey = UUID

    O canal vira a variável channel, usada em decisões e na visibilidade das telas. O businessKey é gerado pelo serviço.

  6. 6
    POST /process-definition/key/Journey_<hex>/start

    Inicia a versão mais recente implantada da jornada. A instância fica presa a essa versão até o fim.

  7. 7
    transação até a primeira espera

    O motor executa decisões e integrações síncronas até parar numa tela, numa integração em segundo plano, num envio Kafka ou numa espera de mensagem.

  8. 8
    após o commit: HSET ej:inst:{pid} · EXPIRE 24 h

    Com a transação confirmada, o motor grava o estado da instância no Redis. A validade de 24 h é renovada a cada nova escrita.

  9. 9
    { id: processInstanceId }

    O motor devolve o identificador da instância.

  10. 10
    Resolver a etapa pelo motor

    O ms-journey descobre a primeira etapa direto no motor e, se for uma tela, pede a tela resolvida ao ms-espec-registry.

  11. 11
    GET /journeys/{jid}/flow

    Busca o fluxo publicado, recortado para o canal: canais atendidos e nós com id, tipo, nome e variáveis de entrada.

  12. 12
    200 { processInstanceId, businessKey, flow, step }

    A resposta já traz a primeira etapa: o canal começa a desenhar sem outra chamada.

GET/instances/{processInstanceId}/current-step

Etapa atual

Diz onde a instância está agora. O canal usa esta rota em três situações: no polling de uma etapa em espera, para retomar uma jornada (app reaberto, sessão nova) e no Tentar novamente de uma tela cuja fonte de dados falhou.

Como o ms-journey responde

Estado no RedisRespostaCusto
WAITING ou FAILEDWAITING com nodeId, nodeName e nodeType1 leitura no Redis
USER_TASKUSER_TASK com a tela montada na horamotor + ms-espec-registry (+ fontes de dados da tela)
sem chaveo que o motor disser: USER_TASK, WAITING ou ENDEDmotor + ms-espec-registry

A chave some quando a instância termina, depois de 24 h sem nenhuma escrita do motor ou se o Redis estiver fora do ar. Nos três casos o motor responde: o resultado é o mesmo, só mais caro.

Polling recomendado

Comece consultando a cada 3 s, que é o ritmo do worker de mensagens, e aumente até 10 s. Defina um limite de espera pela experiência do canal. Passado o limite, avise a pessoa e permita continuar depois com o mesmo processInstanceId.

Uma tarefa assíncrona em incidente continua aparecendo como WAITING até a operação tratar no Diagnóstico. O limite de espera do canal cobre esse caso.

Resolver a etapa pelo motor

Iniciar, consultar com tela aberta, concluir e voltar usam a mesma resolução. Ela vale sempre a verdade do motor, nunca o cache.

  1. 1
    GET /process-instance/{pid}

    Confirma que a instância existe e obtém a definição. Se o motor responder 404, a etapa é ENDED.

  2. 2
    GET ej:def:{definitionId}:versionTag

    A versão da definição é imutável e fica em cache no Redis, sem expiração.

  3. 3
    GET /process-definition/{definitionId}

    Na primeira vez, o ms-journey lê o versionTag ("v3") no motor.

  4. 4
    SET ej:def:{definitionId}:versionTag v3

    E guarda no cache para as próximas resoluções.

  5. 5
    GET /task?processInstanceId={pid}

    Procura tarefas de usuário abertas. Só a primeira é entregue.

  6. 6
    GET /process-instance/{pid}/variables

    Lê as variáveis da instância (form_*, data_*, channel). Listas gravadas como Json são lidas como texto.

  7. 7
    POST …/versions/3/nodes/{nodeId}/form/resolve

    Pede a tela do nó na versão da instância, com as variáveis atuais.

  8. 8
    journey_version · published_screen

    O registro lê o snapshot da versão e a tela publicada daquele nó.

  9. 9
    GET fontes de dados da tela

    Se a tela declara fontes de dados, o registro as chama agora, em sequência, e registra cada consulta em data_source_call.

  10. 10
    placeholders · vínculos · listas · fontes = {}

    Resolve a árvore e esvazia dataSources: endereço e credencial das fontes nunca saem do servidor.

  11. 11
    GET /process-instance/{pid}/activity-instances

    Descobre em que atividade o motor está parado.

  12. 12
    GET /journeys/{jid}/flow

    Busca nome e tipo desse nó no fluxo publicado.

POST/instances/{processInstanceId}/tasks/{taskId}/complete

Concluir a tela

Envia o que a pessoa preencheu. A resposta já é a próxima etapa.

Corpo

  • Cada chave de answers é o caminho do vínculo twoWay sem o form.: o campo ligado a form.email vai como email.
  • Só entram campos visíveis e ativos. Valores nulos são ignorados.
  • Se o botão de envio tiver params: { "path": "form.botao", "value": "confirmar" }, acrescente botao: "confirmar".
  • Na lista de seleção, vão o item (vínculo value) e a ação (vínculo action).
  • O servidor tipa cada resposta pela tela publicada: campo de texto com inputMode number ou decimal vira número, ui.checkbox vira booleano, o resto vira texto.

POST/instances/{processInstanceId}/back

Voltar

  • A tela anterior é a última tela concluída antes da atual abrir.
  • Uma tela que já foi destino de um Voltar não serve de novo: dois Voltar seguidos não reabrem a mesma tela.

Como a tela é montada

Quando a etapa é uma tela, o ms-journey pede ao ms-espec-registry a tela do nó na versão da instância, com as variáveis atuais. O ms-espec-registry monta a tela em seis passos e o ms-journey a repassa ao canal sem ler o conteúdo.

schemaVersion, catalogVersionVersão do formato e do catálogo de componentes. Hoje, 1.0.0.
journeyId, journeyVersion, uiStepIdJornada, versão e nó a que a tela pertence.
status, publishedAtSituação e data da publicação.
supportedTargets, minRendererVersionAlvos que podem desenhar a tela e a versão mínima do renderizador em cada um.
dataSourcesSempre {} para o canal.
dataÁrvore de tuplas [tipo, atributos] ou [tipo, atributos, filhos], com raiz ui.screen.

O que o canal faz com a tela

  1. Confere a compatibilidade. O alvo do canal (react.web, react.mobile, flutter.web, flutter.mobile ou whatsapp) precisa estar em supportedTargets, e a versão do renderizador precisa atender minRendererVersion. Se não atender, não desenhe a tela pela metade.
  2. Desenha os componentes. Associa cada tipo do catálogo v1 a um componente do canal. Textos e valores já chegam resolvidos.
  3. Guarda o estado dos campos. O que a pessoa digita nos campos com vínculo twoWay em form.* vira resposta.
  4. Avalia condições. $visibility e $active usam { rule, path, value } com equals, notEquals, in e notIn. Para form.x, o valor atual do campo; para data.x, form.context.data["data_x"]; para channel, o canal. Num contêiner, vale para tudo o que está dentro. disabled: true prevalece sobre $active.
  5. Valida antes de enviar. required, maxLength e as regras de validation (cada uma com rule, value e message), só nos campos visíveis e ativos.
  6. Executa as ações.
AçãoO que o canal faz
action.submitValida os campos visíveis e ativos e chama o concluir com as respostas.
action.navigateCom params.route = "voltar", chama o Voltar. Outros destinos são rotas do próprio canal.
action.retryPede a etapa atual de novo (GET current-step), o que remonta a tela. Aparece no componente com loadError obrigatório.
action.openUrlAbre params.url, só http ou https e de domínio permitido pelo canal.
action.setValueGrava params.value em params.path (só form.*), sem falar com o serviço.
action.trackEnvia params.event para a telemetria do canal, sem dados sensíveis.
action.dismissEsconde o componente (por exemplo, um aviso dispensável).

Integrações assíncronas

Integrações assíncronas não seguram a chamada do canal. A transação termina, a instância fica em espera e o canal recebe WAITING. Quando o motor retoma sozinho (job, worker Kafka, mensagem recebida, limite de espera), o Redis muda e o próximo polling encontra a nova etapa.

Estado em Redis

O ms-runtime-camunda grava o estado de cada instância num Redis exclusivo da plataforma, sempre depois que a transação do motor é confirmada. O ms-journey lê esse estado para responder etapas em espera sem chamar o motor. O contrato com o canal não muda: o detalhe das tarefas assíncronas serve ao Diagnóstico e ao monitoramento.

Garantias

  • Só depois do commit. A escrita é registrada como listener da transação confirmada: um rollback nunca aparece no Redis.
  • O motor é a fonte da verdade. Chave ausente ou Redis fora do ar: o ms-journey resolve pelo motor. Nada quebra sem o Redis.
  • Ordem preservada. Worker e executor de jobs escrevem em threads diferentes; a escrita só vale se o evento for mais novo que o gravado.
  • Operações que mudam a instância não usam o cache. Iniciar, concluir e voltar sempre resolvem a etapa pelo motor.

Erros

Os erros chegam de dois jeitos: uma resposta 200 com errorMessage (a etapa voltou igual) ou um status HTTP de erro. Erros gerados no ms-journey e no ms-espec-registry têm o corpo { timestamp, status, code, message }. Erros repassados do motor trazem { type, message }.

Comportamentos a considerar

Instância inexistente
GET current-step de um processInstanceId que não existe devolve ENDED, não 404.
Telas em paralelo
Só a primeira tarefa de usuário aberta é entregue.
Incidente em espera
Uma tarefa assíncrona que esgotou as tentativas fica em incidente. O canal continua vendo WAITING até a operação tratar no Diagnóstico.
Versão
As telas vêm da versão da instância. GET /flow, a checagem de escritas do Voltar e o nome de uma espera resolvida pelo motor usam a publicação atual.
Autenticação
O ms-journey ainda não exige credencial (forma em definição). Exponha-o só por trás do BFF do canal.
Tempo limite
O ms-journey não define tempo limite próprio nas chamadas ao motor e ao registro. Defina o do BFF considerando as integrações síncronas da jornada.
Canal informado
channelType não é conferido contra flow.channelTypes. Use um dos canais que a jornada atende.
Envio duplo
Dois envios simultâneos da mesma tela: o segundo recebe 200 com errorMessage do motor, não 409.
Redis indisponível
Sem efeito funcional: o ms-journey resolve pelo motor e o polling volta a custar chamadas ao motor.
