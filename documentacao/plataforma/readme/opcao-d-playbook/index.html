Playbook do canal

O que o seu canal faz em cada situação de uma jornada do Elastic Journey: o que chamar, o que esperar de volta e o que evitar. Os diagramas mostram o que a plataforma faz por trás de cada resposta.

O laço do canal

Todo canal é o mesmo laço: receber a etapa, decidir pelo tipo, agir, receber a próxima. As seis operações do ms-journey cabem nele.

OperaçãoRota
Fluxo da jornadaGET /journeys/{journeyId}/flow
IniciarPOST /journeys/{journeyId}/instances?channelType=…
Etapa atualGET /instances/{processInstanceId}/current-step
Concluir a telaPOST /instances/{processInstanceId}/tasks/{taskId}/complete
VoltarPOST /instances/{processInstanceId}/back
EncerrarDELETE /instances/{processInstanceId}
O laço em TypeScript
const BASE = 'http://localhost:8085/api/v1';

async function chamar(method: string, path: string, body?: unknown) {
  const resposta = await fetch(BASE + path, {
    method,
    headers: { 'content-type': 'application/json' },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  const texto = await resposta.text();
  const json = texto ? JSON.parse(texto) : null;
  if (!resposta.ok) throw new Error(json?.message ?? `HTTP ${resposta.status}`);
  return json;
}

let { processInstanceId, step } = await chamar(
  'POST', `/journeys/${journeyId}/instances?channelType=WEB`, { cpf, nomeCliente });

let espera = 3000;
while (step.type !== 'ENDED') {
  if (step.type === 'WAITING') {
    await new Promise((fim) => setTimeout(fim, espera));
    espera = Math.min(espera * 1.5, 10000);
    step = await chamar('GET', `/instances/${processInstanceId}/current-step`);
    continue;
  }
  espera = 3000;
  const acao = await desenharTela(step.form, step.errorMessage); // a parte do seu canal
  if (acao.tipo === 'voltar') step = await chamar('POST', `/instances/${processInstanceId}/back`);
  else if (acao.tipo === 'tentar') step = await chamar('GET', `/instances/${processInstanceId}/current-step`);
  else step = await chamar('POST', `/instances/${processInstanceId}/tasks/${step.taskId}/complete`, { answers: acao.respostas });
}

Situações

Início

Iniciar a jornada

QuandoA pessoa entra no fluxo pelo canal.

Faça
  1. Se precisar saber o que a jornada pede, consulte GET /journeys/{journeyId}/flow: o nó START lista as variáveis de entrada.
  2. Chame POST /journeys/{journeyId}/instances?channelType=… com as variáveis no corpo.
  3. Guarde o processInstanceId junto da sessão da pessoa.
  4. Trate step como qualquer etapa recebida.
Requisição
curl -X POST "http://localhost:8085/api/v1/journeys/{journeyId}/instances?channelType=WEB" \
  -H "content-type: application/json" \
  -d '{ "cpf": "12345678900", "nomeCliente": "Ana Souza" }'
Evite
  • Enviar channel no corpo: o nome é reservado e vem de channelType.
  • Supor que a primeira etapa é sempre uma tela: ela pode ser uma espera.

Por trásO ms-espec-registry tipa as variáveis, o motor executa até a primeira espera e grava o estado no Redis, e o ms-journey resolve a etapa antes de responder. Ver sequência.

Início

Retomar uma jornada

QuandoO app foi reaberto, a sessão caiu ou a pessoa voltou outro dia.

Faça
  1. Chame GET /instances/{processInstanceId}/current-step com o id guardado.
  2. Trate a resposta como uma etapa recebida: tela, espera ou fim.
Requisição
curl "http://localhost:8085/api/v1/instances/{processInstanceId}/current-step"
Evite
  • Iniciar uma nova instância para a mesma pessoa sem encerrar a anterior.

Por trásSe a instância está parada há mais de 24 h, a chave do Redis já expirou: o ms-journey resolve pelo motor e a resposta é a mesma.

Erros

Variável de entrada recusada

QuandoO início responde 409 com SIMULATION_STATE_ERROR.

Faça
  1. Leia a lista em message: são as variáveis declaradas que faltaram.
  2. Corrija a chamada. Toda variável declarada no Início é obrigatória.
Resposta 409
{
  "timestamp": "2026-10-07T14:30:51.204-03:00",
  "status": 409,
  "code": "SIMULATION_STATE_ERROR",
  "message": "Variáveis de entrada obrigatórias não informadas: [cpf]"
}

Por trásA mesma resposta vale para jornada sem publicação. Nada é criado no motor.

Tela

Desenhar a tela recebida

QuandoA etapa é USER_TASK.

Faça
  1. Confira se o alvo do canal está em sdui.supportedTargets e se o renderizador atende minRendererVersion.
  2. Percorra sdui.data: tuplas [tipo, atributos, filhos] com raiz ui.screen.
  3. Use textos e valores como vieram: placeholders e vínculos já estão resolvidos.
  4. Reavalie $visibility e $active enquanto a pessoa preenche. Para data.x, use form.context.data["data_x"]; para channel, o seu canal.
  5. Se vier errorMessage, mostre a mensagem acima da tela.
Evite
  • Desenhar a tela pela metade quando ela não é compatível com o canal.
  • Buscar dados por conta própria: dataSources chega vazio porque o servidor já buscou.

Por trásA tela foi montada no ms-espec-registry em seis passos. Ver a tela por dentro.

Tela

Enviar a tela

QuandoA pessoa toca num botão com action.submit.

Faça
  1. Valide required, maxLength e as regras de validation dos campos visíveis e ativos.
  2. Monte answers com os vínculos twoWay, sem o form.: form.email vira email.
  3. Se o botão tiver params.path e params.value, acrescente esse valor.
  4. Chame o concluir com o taskId da tela e desabilite o botão até a resposta.
  5. A resposta é a próxima etapa: trate como etapa recebida.
Requisição
curl -X POST "http://localhost:8085/api/v1/instances/{processInstanceId}/tasks/{taskId}/complete" \
  -H "content-type: application/json" \
  -d '{ "answers": { "email": "ana.souza@exemplo.com", "aceite": true } }'
Evite
  • Enviar campos ocultos ou desabilitados.
  • Reaproveitar um taskId antigo: ele muda a cada abertura da tela.

Por trásO ms-journey confere o taskId, o ms-espec-registry tipa as respostas e o motor conclui a tarefa, executando as integrações síncronas do trecho. Ver sequência.

Tela

Recebi errorMessage

QuandoA resposta é 200, mas traz a mesma etapa com errorMessage.

Faça
  1. Mostre a mensagem para a pessoa.
  2. Mantenha o que ela já preencheu.
  3. Permita enviar de novo: o próximo envio repete a operação.
Resposta 200
{
  "type": "USER_TASK",
  "taskId": "8f1c2d4e-8b3d-11f1-9c4e-0242ac120002",
  "nodeId": "Node_5b0e…",
  "nodeName": "Seus dados",
  "nodeType": "USER_TASK",
  "form": { "name": "Seus dados", "sdui": { … }, "context": { … } },
  "errorMessage": "O serviço api.exemplo não respondeu dentro do tempo limite."
}

Por trásAparece quando uma integração síncrona ficou sem resposta e não tinha “Se falhar” (o motor desfez tudo), quando o Voltar é recusado ou num envio simultâneo da mesma tela.

Tela

Uma fonte de dados falhou

QuandoUm select ou lista chega com loadError.

Faça
  1. Mostre loadError.message no próprio componente.
  2. Se loadError.required for verdadeiro, ofereça “Tentar novamente” e não deixe enviar a tela.
  3. “Tentar novamente” é action.retry: chame GET current-step e desenhe a tela de novo.
Componente com loadError
{ "options": [], "loadError": { "message": "Não foi possível carregar os planos agora.", "required": true } }

Por trásA busca acontece no ms-espec-registry a cada montagem da tela e fica registrada em data_source_call. O motor não sabe da falha.

Navegação

Botão Voltar

QuandoA pessoa toca num botão com action.navigate e params.route igual a "voltar".

Faça
  1. Chame POST /instances/{processInstanceId}/back.
  2. Desenhe a etapa recebida: a tela anterior, com os valores que já tinham sido preenchidos.
  3. Se vier a mesma tela com errorMessage, mostre o motivo e continue nela.
Requisição
curl -X POST "http://localhost:8085/api/v1/instances/{processInstanceId}/back"
Evite
  • Simular o Voltar só no canal, reabrindo uma tela guardada: a tela anterior precisa ser reaberta no motor.

Por trásO histórico do motor decide: última tela concluída antes da atual, sem integração de escrita concluída entre as duas. Ver sequência.

Navegação

Links e outras ações

QuandoA tela traz action.openUrl, action.navigate para outro destino, action.track, action.setValue ou action.dismiss.

Faça
  1. openUrl: abra só URLs http ou https de domínios que o canal permite.
  2. navigate com outro destino: é uma rota do próprio canal.
  3. track: envie params.event para a telemetria, sem dados sensíveis.
  4. setValue: grave params.value em params.path (só form.*).
  5. dismiss: esconda o componente.

Por trásNenhuma dessas ações chama o ms-journey.

Espera

Recebi WAITING

QuandoA jornada está processando algo fora da tela: integração em segundo plano, envio Kafka ou espera de mensagem.

Faça
  1. Mostre uma tela de espera do próprio canal. nodeName ajuda a escrever a mensagem.
  2. Comece o polling com GET current-step.
  3. Quando vier outra etapa, siga o laço.
Resposta 200
{
  "type": "WAITING",
  "taskId": null,
  "nodeId": "Node_9d3c…",
  "nodeName": "Solicitar troca",
  "nodeType": "SERVICE_TASK",
  "form": null,
  "errorMessage": null
}

Por trásEm espera, cada consulta é respondida pelo Redis, sem chamar o motor. nodeType é SERVICE_TASK (integração ou envio) ou RECEIVE_TASK (espera de mensagem).

Espera

Quanto tempo esperar

QuandoA etapa continua WAITING por mais tempo que o esperado.

Faça
  1. Consulte a cada 3 s, que é o ritmo do worker de mensagens, e aumente até 10 s.
  2. Tenha um limite de espera definido pela experiência do canal.
  3. Passado o limite, avise a pessoa e permita continuar depois, com o mesmo processInstanceId.
Evite
  • Consultar sem intervalo.
  • Esperar para sempre: uma tarefa em incidente fica WAITING até a operação tratar no Diagnóstico.

Por trásEnvios Kafka tentam até 2 vezes de novo; esgotados, seguem pelo “Se falhar” ou viram incidente. Esperas de mensagem podem ter limite, que leva a outro caminho do fluxo.

Fim

Recebi ENDED

QuandoA jornada terminou.

Faça
  1. Mostre a conclusão no canal.
  2. Descarte o processInstanceId guardado.
Resposta 200
{
  "type": "ENDED",
  "taskId": null,
  "nodeId": null,
  "nodeName": null,
  "nodeType": null,
  "form": null,
  "errorMessage": null
}
Evite
  • Tratar ENDED como sucesso garantido de negócio: ele também vem para um id que não existe.

Por trásNo fim, o motor apaga as chaves da instância no Redis; a consulta vai ao motor, que responde 404, e o ms-journey devolve ENDED.

Fim

A pessoa desistiu

QuandoA pessoa cancela o fluxo ou a sessão expira por regra do canal.

Faça
  1. Chame DELETE /instances/{processInstanceId}.
  2. Encerrar uma instância que já terminou não é erro.
Requisição
curl -X DELETE "http://localhost:8085/api/v1/instances/{processInstanceId}"
Erros

Recebi 409

QuandoUm envio ou Voltar responde 409 JOURNEY_STATE_ERROR.

Faça
  1. Chame GET current-step.
  2. Siga a partir da etapa atual.
Resposta 409
{
  "timestamp": "2026-10-07T14:32:08.512-03:00",
  "status": 409,
  "code": "JOURNEY_STATE_ERROR",
  "message": "Task 8f1c2d4e-… não é o passo ativo atual da instância a41f0c2e-…"
}

Por trásO taskId enviado não é o da tela aberta (envio repetido, aba antiga) ou o Voltar foi pedido fora de uma tela.

Erros

Recebi 502 ou 500

QuandoO serviço não conseguiu atender.

Faça
  1. Mostre uma mensagem genérica e ofereça tentar de novo mais tarde.
  2. Registre code e message para suporte.
  3. No início, SYNCHRONOUS_CHAIN_UNSUPPORTED é um problema da jornada: avise o time que a publicou.
Resposta 502
{
  "timestamp": "2026-10-07T14:35:12.007-03:00",
  "status": 502,
  "code": "UPSTREAM_UNAVAILABLE",
  "message": "I/O error on POST request for \"http://localhost:8080/engine-rest/…\": Connection refused"
}

Por trásUPSTREAM_UNAVAILABLE: ms-espec-registry ou motor fora do ar. Um 5xx com corpo { type, message } no início é uma integração síncrona sem resposta: a instância não foi criada.

Por trás de cada resposta

O que o ms-journey, o ms-espec-registry, o motor e o Redis fazem a cada chamada. Em azul, as interações com o Redis.

  1. 1
    POST /journeys/{jid}/instances?channelType=WEB

    O canal envia as variáveis de entrada no corpo e informa o canal na query.

  2. 2
    POST /journeys/{jid}/start-variables/convert

    O ms-journey pede ao ms-espec-registry para validar e tipar as variáveis de entrada.

  3. 3
    journey_publication · nó START

    O registro lê a publicação atual, confere se a jornada não termina só com integrações síncronas (senão, 502) e aplica os tipos declarados no Início.

  4. 4
    { data_cpf, data_nomeCliente } tipadas

    Toda variável declarada é obrigatória: faltando alguma, a resposta é 409 e nada é criado. Chaves extras também entram, como data_.

  5. 5
    + channel = WEB · businessKey = UUID

    O canal vira a variável channel, usada em decisões e na visibilidade das telas. O businessKey é gerado pelo serviço.

  6. 6
    POST /process-definition/key/Journey_<hex>/start

    Inicia a versão mais recente implantada da jornada. A instância fica presa a essa versão até o fim.

  7. 7
    transação até a primeira espera

    O motor executa decisões e integrações síncronas até parar numa tela, numa integração em segundo plano, num envio Kafka ou numa espera de mensagem.

  8. 8
    após o commit: HSET ej:inst:{pid} · EXPIRE 24 h

    Com a transação confirmada, o motor grava o estado da instância no Redis. A validade de 24 h é renovada a cada nova escrita.

  9. 9
    { id: processInstanceId }

    O motor devolve o identificador da instância.

  10. 10
    Resolver a etapa pelo motor

    O ms-journey descobre a primeira etapa direto no motor e, se for uma tela, pede a tela resolvida ao ms-espec-registry.

  11. 11
    GET /journeys/{jid}/flow

    Busca o fluxo publicado, recortado para o canal: canais atendidos e nós com id, tipo, nome e variáveis de entrada.

  12. 12
    200 { processInstanceId, businessKey, flow, step }

    A resposta já traz a primeira etapa: o canal começa a desenhar sem outra chamada.

  1. 1
    GET /instances/{pid}/current-step

    O canal pergunta onde a instância está. É a chamada do polling, da retomada e do Tentar novamente.

  2. 2
    HGETALL ej:inst:{pid}

    O ms-journey lê primeiro o estado que o motor gravou no Redis.

  3. 3
    WAITING · nodeId, nodeName, nodeType

    Em espera, o Redis já tem tudo o que o canal recebe.

  4. 4
    200 WAITING

    Resposta imediata, sem chamar o motor nem o ms-espec-registry. Um incidente (FAILED) também chega ao canal como WAITING.

  5. 5
    USER_TASK · taskId

    Há tela aberta. A tela depende das variáveis e das fontes de dados, por isso é montada na hora.

  6. 6
    Resolver a etapa pelo motor

    A resolução completa de sempre: motor e ms-espec-registry.

  7. 7
    (vazio)

    Sem chave, o ms-journey não presume nada.

  8. 8
    Resolver a etapa pelo motor

    O motor é a fonte da verdade: 404 vira ENDED, e uma instância parada há mais de 24 h é resolvida normalmente.

  1. 1
    GET /process-instance/{pid}

    Confirma que a instância existe e obtém a definição. Se o motor responder 404, a etapa é ENDED.

  2. 2
    GET ej:def:{definitionId}:versionTag

    A versão da definição é imutável e fica em cache no Redis, sem expiração.

  3. 3
    GET /process-definition/{definitionId}

    Na primeira vez, o ms-journey lê o versionTag ("v3") no motor.

  4. 4
    SET ej:def:{definitionId}:versionTag v3

    E guarda no cache para as próximas resoluções.

  5. 5
    GET /task?processInstanceId={pid}

    Procura tarefas de usuário abertas. Só a primeira é entregue.

  6. 6
    GET /process-instance/{pid}/variables

    Lê as variáveis da instância (form_*, data_*, channel). Listas gravadas como Json são lidas como texto.

  7. 7
    POST …/versions/3/nodes/{nodeId}/form/resolve

    Pede a tela do nó na versão da instância, com as variáveis atuais.

  8. 8
    journey_version · published_screen

    O registro lê o snapshot da versão e a tela publicada daquele nó.

  9. 9
    GET fontes de dados da tela

    Se a tela declara fontes de dados, o registro as chama agora, em sequência, e registra cada consulta em data_source_call.

  10. 10
    placeholders · vínculos · listas · fontes = {}

    Resolve a árvore e esvazia dataSources: endereço e credencial das fontes nunca saem do servidor.

  11. 11
    GET /process-instance/{pid}/activity-instances

    Descobre em que atividade o motor está parado.

  12. 12
    GET /journeys/{jid}/flow

    Busca nome e tipo desse nó no fluxo publicado.

  1. 1
    POST /instances/{pid}/tasks/{taskId}/complete

    O canal envia { answers } com o que a pessoa preencheu, usando o taskId da tela.

  2. 2
    Resolver a etapa pelo motor

    O ms-journey resolve a etapa atual para conferir se o taskId ainda é o da tela aberta.

  3. 3
    taskId é o da tela aberta? senão 409

    Envio repetido ou tela antiga: 409 e nada muda.

  4. 4
    POST …/versions/3/nodes/{nodeId}/answers/convert

    O registro tipa cada resposta pela tela publicada (número, booleano ou texto) e devolve form_.

  5. 5
    POST /task/{taskId}/complete { variables }

    Conclui a tarefa no motor com as variáveis tipadas.

  6. 6
    transação: decisões e integrações síncronas

    O motor segue o fluxo na mesma transação: decisões e integrações REST síncronas, até a próxima espera.

  7. 7
    REST síncrono do trecho

    Cada integração síncrona soma seu tempo à chamada do canal.

  8. 8
    após o commit: HSET ej:inst:{pid} · EXPIRE 24 h

    O novo estado vai para o Redis e a validade é renovada.

  9. 9
    Resolver a etapa pelo motor

    A próxima etapa é resolvida pelo motor, nunca pelo cache.

  10. 10
    200 próxima etapa

    USER_TASK, WAITING ou ENDED.

  11. 11
    500 { message } · rollback

    O motor desfaz a transação inteira: nada avança e o Redis não muda.

  12. 12
    200 mesma etapa + errorMessage

    O canal mostra a mensagem e mantém o que a pessoa preencheu; um novo envio tenta de novo.

  1. 1
    POST /instances/{pid}/back

    Botão com action.navigate e route "voltar".

  2. 2
    Resolver a etapa pelo motor

    A instância precisa estar numa tela; senão, 409.

  3. 3
    GET /process-instance/{pid}/variables

    Lê _voltasConsumidas: telas que já foram destino de um Voltar.

  4. 4
    GET /history/activity-instance?processInstanceId

    Lê o histórico da instância em ordem: telas, integrações e horários.

  5. 5
    GET /journeys/{jid}/flow

    Identifica as integrações de escrita: toda integração que não é REST GET, inclusive envios Kafka.

  6. 6
    BackNavigation.decide

    Escolhe a última tela concluída antes da atual e confere se nenhuma escrita foi concluída entre as duas.

  7. 7
    GET /process-instance/{pid}/activity-instances

    Acha a instância da tela aberta, que será cancelada.

  8. 8
    POST /process-instance/{pid}/modification

    Reabre a tela anterior e cancela a atual numa operação só.

  9. 9
    após o commit: HSET USER_TASK · novo taskId

    O Redis passa a apontar a tela reaberta.

  10. 10
    PUT …/variables/_voltasConsumidas

    Marca a tela de destino, para um segundo Voltar não reabrir a mesma.

  11. 11
    Resolver a etapa pelo motor

    A tela anterior volta com os valores já preenchidos, pelos vínculos.

  12. 12
    200 mesma etapa + errorMessage

    O motivo vem em errorMessage e a instância não muda.

  1. 1
    POST …/tasks/{taskId}/complete

    O envio da tela dispara o trecho seguinte do fluxo.

  2. 2
    POST /task/{taskId}/complete

    Validação e conversão das respostas acontecem antes, como em Concluir.

  3. 3
    integração REST na transação

    A chamada roda dentro da transação, com tempo de conexão (padrão 2 s) e de resposta (padrão 10 s).

  4. 4
    POST https://api.exemplo/… · Idempotency-Key

    Em POST, a mesma Idempotency-Key vai em todas as tentativas.

  5. 5
    503 · 429 · 502 · 504 · sem conexão · tempo esgotado

    Só falhas passageiras se repetem, até 2 vezes, se a etapa permitir.

  6. 6
    espera 1×, 2× o intervalo (±20%)

    Intervalo padrão 1 s, máximo 5 s.

  7. 7
    segue o fluxo · status disponível

    A resposta é de negócio: o mapeamento de saída roda e as decisões podem usar o status.

  8. 8
    200 próxima etapa

    O canal recebe a etapa seguinte normalmente.

  9. 9
    segue pelo caminho “Se falhar”

    O fluxo segue pelo caminho de falha desenhado pelo autor, por exemplo uma tela de erro.

  10. 10
    500 { message } · rollback

    A transação inteira é desfeita.

  11. 11
    200 mesma etapa + errorMessage

    Exemplo de mensagem: “O serviço api.exemplo não respondeu dentro do tempo limite (3 tentativas).”

  1. 1
    POST …/tasks/{taskId}/complete

    A pessoa confirma o plano.

  2. 2
    para na tarefa externa kafka-<nodeId>

    O envio Kafka vira tarefa externa: a transação termina e a instância espera o worker.

  3. 3
    após o commit: WAITING · KAFKA_SEND PENDING

    O estado de espera e o detalhe da tarefa vão para o Redis.

  4. 4
    200 WAITING { nodeName: "Solicitar troca" }

    O canal mostra que está processando e começa o polling.

  5. 5
    GET current-step

    Cada consulta custa uma leitura no Redis.

  6. 6
    worker (a cada 3 s): fetchAndLock

    O worker Kafka busca as tarefas pendentes e trava cada uma por 30 s.

  7. 7
    produce kafka-<nodeId> · key = pid

    Publica o envelope { correlationId, payload } com tempo limite de 5 s e até 2 novas tentativas.

  8. 8
    após o commit: KAFKA_SEND COMPLETED · MESSAGE_WAIT PENDING

    A tarefa externa termina e o fluxo para na espera da resposta.

  9. 9
    mensagem com correlationId = pid

    O sistema externo responde. A leitura só é confirmada depois de tratada.

  10. 10
    correlate ⇒ segue até a próxima tela

    O motor correlaciona pela instância (ou pelo businessKey) e segue o fluxo.

  11. 11
    após o commit: USER_TASK · taskId

A tela por dentro

A tela chega pronta: o ms-espec-registry monta tudo antes de o ms-journey repassar. O que fica com o canal é estado dos campos, condições, validação e ações.

Integrações e o tempo do canal

Síncronas

Rodam dentro do início ou do envio da tela: o canal espera por elas.

ResultadoCom “Se falhar”Sem “Se falhar”
2xx ou 4xxSegue o fluxo. Status e corpo ficam disponíveis para o mapeamento de saída e as decisões.Igual.
5xx, depois das tentativasSegue pelo caminho “Se falhar”.Segue o fluxo normal, com o status disponível para as decisões.
Sem resposta: conexão recusada ou tempo esgotadoSegue pelo caminho “Se falhar”.A etapa falha e a transação é desfeita. Ao concluir uma tela: a mesma tela volta com errorMessage. No início: erro HTTP e a instância não é criada.

Assíncronas

Não seguram a chamada: a etapa fica WAITING até o motor retomar.

Comportamentos a considerar

Instância inexistente
GET current-step de um processInstanceId que não existe devolve ENDED, não 404.
Telas em paralelo
Só a primeira tarefa de usuário aberta é entregue.
Incidente em espera
Uma tarefa assíncrona que esgotou as tentativas fica em incidente. O canal continua vendo WAITING até a operação tratar no Diagnóstico.
Versão
As telas vêm da versão da instância. GET /flow, a checagem de escritas do Voltar e o nome de uma espera resolvida pelo motor usam a publicação atual.
Autenticação
O ms-journey ainda não exige credencial (forma em definição). Exponha-o só por trás do BFF do canal.
Tempo limite
O ms-journey não define tempo limite próprio nas chamadas ao motor e ao registro. Defina o do BFF considerando as integrações síncronas da jornada.
Canal informado
channelType não é conferido contra flow.channelTypes. Use um dos canais que a jornada atende.
Envio duplo
Dois envios simultâneos da mesma tela: o segundo recebe 200 com errorMessage do motor, não 409.
Redis indisponível
Sem efeito funcional: o ms-journey resolve pelo motor e o polling volta a custar chamadas ao motor.
