1Objetivo e escopo

Este documento especifica como um canal digital (site, app ou WhatsApp) executa jornadas publicadas no Elastic Journey por meio do ms-journey: operações, formato das respostas, montagem das telas, efeito das integrações síncronas e assíncronas, erros e as obrigações do canal.

Fica fora do escopo a autoria e a publicação de jornadas, que acontecem no Admin, e a descoberta de jornadas publicadas: o canal já conhece o journeyId.

O comportamento descrito considera o cache de estado em Redis (seção 6.3) como parte da plataforma.

2Convenções

As palavras DEVE, NÃO DEVE, DEVERIA e PODE, em maiúsculas, têm o sentido de obrigação, proibição, recomendação e opção. Requisitos do canal têm identificador CNL-nn; garantias da plataforma, PLT-nn.

Caminhos de API são relativos a http://localhost:8085/api/v1 (ambiente local). {pid} abrevia {processInstanceId}. Nas figuras, setas contínuas são chamadas, tracejadas são respostas, e a cor do cache marca as interações com o Redis.

4Arquitetura de referência

ComponenteResponsabilidade no caminho do canal
ms-journeyÚnica interface do canal. Sem banco: resolve a etapa, valida o envio, converte respostas pelo ms-espec-registry e repassa a tela sem alterá-la.
ms-espec-registryTipa variáveis de entrada e respostas pela publicação; monta a tela da versão da instância; chama as fontes de dados da tela e registra cada consulta.
ms-runtime-camundaExecuta o fluxo (Camunda 7): decisões, integrações REST síncronas e em segundo plano, envio e recebimento Kafka, temporizadores. Grava o estado no Redis depois de cada commit.
RedisExclusivo da plataforma. Estado da instância, detalhe das tarefas assíncronas e versão de cada definição.
Postgres journey_adminpublic.journey_version e public.journey_publication (do Admin, só leitura); espec_registry.published_screen e espec_registry.data_source_call.

CNL-01O canal DEVE chamar somente o ms-journey. NÃO DEVE chamar o motor, o ms-espec-registry ou as fontes de dados diretamente.

5Interface do serviço

5.1Endereço, formato e autenticação

Todas as rotas ficam sob /api/v1. Corpos e respostas são JSON (content-type: application/json). A forma de autenticação está em definição; hoje o serviço não exige credencial.

CNL-20Enquanto a autenticação estiver em definição, o ms-journey DEVE ser exposto apenas por trás do BFF do canal.

5.4Iniciar

POST/journeys/{journeyId}/instances?channelType={canal}

Cria a instância e devolve a primeira etapa resolvida.

Requisição

ParâmetroOndeRegra
journeyIdrotaUUID da jornada publicada.
channelTypequeryWEB, MOBILE ou WHATSAPP. Vira a variável channel. Não é conferido contra flow.channelTypes.
variáveiscorpoObjeto JSON. Declaradas no START: obrigatórias e convertidas (number, boolean; demais como texto). Não declaradas: aceitas, com tipo inferido. Todas viram data_<nome>.

Comportamento

  1. O ms-espec-registry lê a publicação atual, verifica que a jornada não chega ao fim só por integrações síncronas e converte as variáveis.
  2. O ms-journey acrescenta channel e um businessKey (UUID) e inicia a definição Journey_<uuid sem hífens> mais recente.
  3. O motor executa até a primeira espera; depois do commit, grava o estado no Redis.
  4. O ms-journey resolve a primeira etapa pelo motor (6.3) e busca o fluxo.

5.5Etapa atual

GET/instances/{pid}/current-step

Devolve a etapa em que a instância está. Usada no polling de espera, na retomada e no Tentar novamente.

Comportamento

  1. O ms-journey lê ej:inst:{pid} no Redis.
  2. Com state WAITING ou FAILED, responde WAITING com nodeId, nodeName e nodeType, sem chamar o motor.
  3. Com USER_TASK, ou sem chave, resolve a etapa pelo motor (6.3).
  4. Instância inexistente resulta em ENDED.

Resposta

typeCampos preenchidos
USER_TASKtaskId, nodeId, nodeName, nodeType, form
WAITINGnodeId, nodeName, nodeType
ENDEDnenhum
Requisição
curl "http://localhost:8085/api/v1/instances/{processInstanceId}/current-step"
WAITING
{
  "type": "WAITING",
  "taskId": null,
  "nodeId": "Node_9d3c…",
  "nodeName": "Solicitar troca",
  "nodeType": "SERVICE_TASK",
  "form": null,
  "errorMessage": null
}
  1. 1
    GET /instances/{pid}/current-step

    O canal pergunta onde a instância está. É a chamada do polling, da retomada e do Tentar novamente.

  2. 2
    HGETALL ej:inst:{pid}

    O ms-journey lê primeiro o estado que o motor gravou no Redis.

  3. 3
    WAITING · nodeId, nodeName, nodeType

    Em espera, o Redis já tem tudo o que o canal recebe.

  4. 4
    200 WAITING

    Resposta imediata, sem chamar o motor nem o ms-espec-registry. Um incidente (FAILED) também chega ao canal como WAITING.

  5. 5
    USER_TASK · taskId

    Há tela aberta. A tela depende das variáveis e das fontes de dados, por isso é montada na hora.

  6. 6
    Resolver a etapa pelo motor

    A resolução completa de sempre: motor e ms-espec-registry.

  7. 7
    (vazio)

    Sem chave, o ms-journey não presume nada.

  8. 8
    Resolver a etapa pelo motor

    O motor é a fonte da verdade: 404 vira ENDED, e uma instância parada há mais de 24 h é resolvida normalmente.

Resolução da etapa pelo motor

Procedimento comum a iniciar, concluir, voltar e à etapa atual sem atalho de cache.

  1. 1
    GET /process-instance/{pid}

    Confirma que a instância existe e obtém a definição. Se o motor responder 404, a etapa é ENDED.

  2. 2
    GET ej:def:{definitionId}:versionTag

    A versão da definição é imutável e fica em cache no Redis, sem expiração.

  3. 3
    GET /process-definition/{definitionId}

    Na primeira vez, o ms-journey lê o versionTag ("v3") no motor.

  4. 4
    SET ej:def:{definitionId}:versionTag v3

    E guarda no cache para as próximas resoluções.

  5. 5
    GET /task?processInstanceId={pid}

    Procura tarefas de usuário abertas. Só a primeira é entregue.

  6. 6
    GET /process-instance/{pid}/variables

    Lê as variáveis da instância (form_*, data_*, channel). Listas gravadas como Json são lidas como texto.

  7. 7
    POST …/versions/3/nodes/{nodeId}/form/resolve

    Pede a tela do nó na versão da instância, com as variáveis atuais.

  8. 8
    journey_version · published_screen

    O registro lê o snapshot da versão e a tela publicada daquele nó.

  9. 9
    GET fontes de dados da tela

    Se a tela declara fontes de dados, o registro as chama agora, em sequência, e registra cada consulta em data_source_call.

  10. 10
    placeholders · vínculos · listas · fontes = {}

    Resolve a árvore e esvazia dataSources: endereço e credencial das fontes nunca saem do servidor.

  11. 11
    GET /process-instance/{pid}/activity-instances

    Descobre em que atividade o motor está parado.

  12. 12
    GET /journeys/{jid}/flow

    Busca nome e tipo desse nó no fluxo publicado.

5.6Concluir a tela

POST/instances/{pid}/tasks/{taskId}/complete

Conclui a tela aberta com as respostas e devolve a próxima etapa.

Requisição

ParâmetroOndeRegra
taskIdrotaO da etapa exibida. Diferente do aberto: 409.
answerscorpoObjeto { nome: valor }. Nome é o caminho do vínculo sem form.; nulos são ignorados.

Comportamento

  1. O ms-journey resolve a etapa e confere o taskId.
  2. O ms-espec-registry tipa as respostas pela tela publicada: textInput com inputMode number ou decimal vira número; checkbox, booleano; o resto, texto; prefixo form_.
  3. O motor conclui a tarefa e segue o fluxo na mesma transação, executando as integrações síncronas até a próxima espera.
  4. Confirmada a transação, o ms-journey resolve a próxima etapa pelo motor. Falhando, devolve a mesma etapa com errorMessage.

RespostaCondição
200, próxima etapaTransação confirmada.
200, mesma etapa com errorMessageIntegração síncrona sem resposta e sem “Se falhar”; envio simultâneo da mesma tela.
409 JOURNEY_STATE_ERRORtaskId não é o da tela aberta.

curl -X POST "http://localhost:8085/api/v1/instances/{processInstanceId}/tasks/{taskId}/complete" \
  -H "content-type: application/json" \
  -d '{ "answers": { "email": "ana.souza@exemplo.com", "aceite": true } }'
Resposta 200 com errorMessage
{
  "type": "USER_TASK",
  "taskId": "8f1c2d4e-8b3d-11f1-9c4e-0242ac120002",
  "nodeId": "Node_5b0e…",
  "nodeName": "Seus dados",
  "nodeType": "USER_TASK",

}
  1. 1
    POST /instances/{pid}/tasks/{taskId}/complete

    O canal envia { answers } com o que a pessoa preencheu, usando o taskId da tela.

  2. 2
    Resolver a etapa pelo motor

    O ms-journey resolve a etapa atual para conferir se o taskId ainda é o da tela aberta.

  3. 3
    taskId é o da tela aberta? senão 409

    Envio repetido ou tela antiga: 409 e nada muda.

  4. 4
    POST …/versions/3/nodes/{nodeId}/answers/convert

    O registro tipa cada resposta pela tela publicada (número, booleano ou texto) e devolve form_.

  5. 5
    POST /task/{taskId}/complete { variables }

    Conclui a tarefa no motor com as variáveis tipadas.

  6. 6
    transação: decisões e integrações síncronas

    O motor segue o fluxo na mesma transação: decisões e integrações REST síncronas, até a próxima espera.

  7. 7

    Cada integração síncrona soma seu tempo à chamada do canal.

  8. 8

    O novo estado vai para o Redis e a validade é renovada.

  9. 9
    Resolver a etapa pelo motor

    A próxima etapa é resolvida pelo motor, nunca pelo cache.

  10. 10
    200 próxima etapa

    USER_TASK, WAITING ou ENDED.

  11. 11
    500 { message } · rollback

    O motor desfaz a transação inteira: nada avança e o Redis não muda.

  12. 12
    200 mesma etapa + errorMessage

    O canal mostra a mensagem e mantém o que a pessoa preencheu; um novo envio tenta de novo.

CNL-10O canal DEVE enviar em answers só os vínculos twoWay em form.* de campos visíveis e ativos, sem o prefixo form., mais o params do botão de envio quando houver.

CNL-11O canal DEVE enviar o taskId da etapa exibida e DEVERIA impedir envios simultâneos da mesma tela.

CNL-12O canal DEVE exibir errorMessage quando presente e manter os valores preenchidos.

5.7Voltar

POST/instances/{pid}/back

Reabre a tela anterior sem concluir a atual.

Comportamento

  1. A instância precisa estar numa tela (senão, 409).
  2. O alvo é a última tela concluída antes da atual abrir, que ainda não tenha sido destino de um Voltar.
  3. Recusa se, entre as duas telas, houver integração de escrita concluída com sucesso (toda integração que não seja REST GET). Integração que seguiu pelo “Se falhar” não conta.
  4. Permitido: o motor reabre a tela anterior e cancela a atual numa operação; a tela volta com os valores anteriores e novo taskId.

Resposta

RespostaCondição
200, etapa anteriorVoltar permitido.
200, mesma etapa com errorMessageSem tela anterior, ou escrita já registrada.
409Instância fora de uma tela.
Requisição
curl -X POST "http://localhost:8085/api/v1/instances/{processInstanceId}/back"
Recusado
{
  "type": "USER_TASK",
  "taskId": "c27e5f30-8b3d-11f1-9c4e-0242ac120002",
  "nodeId": "Node_e4f1…",
  "nodeName": "Troca confirmada",
  "nodeType": "USER_TASK",
  "form": { "name": "Troca confirmada", "sdui": { … }, "context": { … } },
  "errorMessage": "Não é possível voltar: a operação desta etapa já foi registrada."
}
  1. 1
    POST /instances/{pid}/back

    Botão com action.navigate e route "voltar".

  2. 2
    Resolver a etapa pelo motor

    A instância precisa estar numa tela; senão, 409.

  3. 3
    GET /process-instance/{pid}/variables

    Lê _voltasConsumidas: telas que já foram destino de um Voltar.

  4. 4
    GET /history/activity-instance?processInstanceId

    Lê o histórico da instância em ordem: telas, integrações e horários.

  5. 5
    GET /journeys/{jid}/flow

    Identifica as integrações de escrita: toda integração que não é REST GET, inclusive envios Kafka.

  6. 6
    BackNavigation.decide

    Escolhe a última tela concluída antes da atual e confere se nenhuma escrita foi concluída entre as duas.

  7. 7
    GET /process-instance/{pid}/activity-instances

    Acha a instância da tela aberta, que será cancelada.

  8. 8
    POST /process-instance/{pid}/modification

    Reabre a tela anterior e cancela a atual numa operação só.

  9. 9
    após o commit: HSET USER_TASK · novo taskId

    O Redis passa a apontar a tela reaberta.

  10. 10
    PUT …/variables/_voltasConsumidas

    Marca a tela de destino, para um segundo Voltar não reabrir a mesma.

  11. 11
    Resolver a etapa pelo motor

    A tela anterior volta com os valores já preenchidos, pelos vínculos.

  12. 12
    200 mesma etapa + errorMessage

    O motivo vem em errorMessage e a instância não muda.

CNL-13O canal DEVE chamar o Voltar para action.navigate com route "voltar". NÃO DEVE simular a navegação localmente.

5.8Encerrar

DELETE/instances/{pid}

Cancela a instância. Responde 200 sem corpo e é idempotente. O motor apaga as chaves da instância no Redis.

Requisição
curl -X DELETE "http://localhost:8085/api/v1/instances/{processInstanceId}"

CNL-19O canal DEVERIA encerrar a instância quando a pessoa desistir.

6Modelo de etapa

6.1Objeto etapa

CampoQuandoDescrição
typesempreUSER_TASK (tela), WAITING (espera) ou ENDED (fim).
taskIdUSER_TASKIdentifica a tela aberta e vai na rota do concluir. Muda a cada abertura da tela, inclusive num Voltar.
nodeIdUSER_TASK, WAITINGId do nó no fluxo: o mesmo de flowNodes[].id e de sdui.uiStepId.
nodeNameUSER_TASK, WAITINGNome da etapa no fluxo. Útil para a mensagem de espera e para telemetria.
nodeTypeUSER_TASK, WAITINGUSER_TASK na tela. Na espera: SERVICE_TASK (integração em segundo plano ou envio Kafka) ou RECEIVE_TASK (espera de mensagem).
form.nameUSER_TASKNome da tela.
form.sduiUSER_TASKEnvelope da tela, já resolvido pelo servidor.
form.contextUSER_TASKValores atuais das variáveis que a tela usa, com o nome no motor: data_x para data.x, form_x para form.x, channel. form e data trazem o mesmo mapa.
form.id, form.descriptionUSER_TASKPresentes, sempre null.
errorMessagequando houverMensagem para a pessoa: a etapa voltou igual (integração que falhou ao concluir, Voltar recusado).

PLT-01Iniciar (em step), etapa atual, concluir e voltar devolvem o mesmo objeto etapa.

6.2Tipos e transições

CNL-05O canal DEVE tratar os três tipos de etapa em qualquer resposta, inclusive na do início.

6.3Cache de estado

12Comportamentos e limites

Instância inexistente
GET current-step de um processInstanceId que não existe devolve ENDED, não 404.
Telas em paralelo
Só a primeira tarefa de usuário aberta é entregue.
Incidente em espera
Uma tarefa assíncrona que esgotou as tentativas fica em incidente. O canal continua vendo WAITING até a operação tratar no Diagnóstico.
Versão
As telas vêm da versão da instância. GET /flow, a checagem de escritas do Voltar e o nome de uma espera resolvida pelo motor usam a publicação atual.
Autenticação
O ms-journey ainda não exige credencial (forma em definição). Exponha-o só por trás do BFF do canal.
Tempo limite
O ms-journey não define tempo limite próprio nas chamadas ao motor e ao registro. Defina o do BFF considerando as integrações síncronas da jornada.
Canal informado
channelType não é conferido contra flow.channelTypes. Use um dos canais que a jornada atende.
Envio duplo
Dois envios simultâneos da mesma tela: o segundo recebe 200 com errorMessage do motor, não 409.
Redis indisponível
Sem efeito funcional: o ms-journey resolve pelo motor e o polling volta a custar chamadas ao motor.

A.5 Fonte de dados que falhou

Se a fonte não responde, responde fora de 2xx ou devolve algo ilegível, a tela é entregue mesmo assim: a lista vem vazia e o componente recebe loadError.

Tela publicada
"dataSources": {
  "planos": { "url": "https://api.exemplo/planos?linha={linha}",
              "params": { "linha": "{{form.linha}}" },
              "timeoutMs": 3000, "required": true,
              "errorMessage": "Não foi possível carregar os planos agora." }

  • A mensagem vem de errorMessage da fonte; sem ela, “Não foi possível carregar as informações agora.”.
  • Com required: true, a etapa não pode ser enviada enquanto a fonte não carregar. O canal oferece “Tentar novamente” no próprio componente.
  • “Tentar novamente” dispara action.retry, que é um novo GET current-step: a tela é montada de novo e a fonte é chamada outra vez.
  • A falha não vira erro HTTP nem toca a instância: o motor não sabe que a fonte falhou.

const BASE = 'http://localhost:8085/api/v1';

async function chamar(method: string, path: string, body?: unknown) {
  const resposta = await fetch(BASE + path, {
    method,
    headers: { 'content-type': 'application/json' },
    body: body === undefined ? undefined : JSON.stringify(body),
  });
  const texto = await resposta.text();
  const json = texto ? JSON.parse(texto) : null;
  if (!resposta.ok) throw new Error(json?.message ?? `HTTP ${resposta.status}`);
  return json;
}

let { processInstanceId, step } = await chamar(
  'POST', `/journeys/${journeyId}/instances?channelType=WEB`, { cpf, nomeCliente });

let espera = 3000;
while (step.type !== 'ENDED') {
  if (step.type === 'WAITING') {
    await new Promise((fim) => setTimeout(fim, espera));
    espera = Math.min(espera * 1.5, 10000);
    step = await chamar('GET', `/instances/${processInstanceId}/current-step`);
    continue;
  }
  espera = 3000;
  const acao = await desenharTela(step.form, step.errorMessage); // a parte do seu canal
  if (acao.tipo === 'voltar') step = await chamar('POST', `/instances/${processInstanceId}/back`);
  else if (acao.tipo === 'tentar') step = await chamar('GET', `/instances/${processInstanceId}/current-step`);
  else step = await chamar('POST', `/instances/${processInstanceId}/tasks/${step.taskId}/complete`, { answers: acao.respostas });
