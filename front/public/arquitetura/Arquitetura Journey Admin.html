Quem fala com quem

Autoria/Admin e Canais Digitais são dois caminhos de execução independentes que convergem no mesmo motor Camunda. O ms-espec-registry é a peça que atravessa os dois mundos.

Ajustes de responsabilidade

Pontos de atenção para as próximas decisões

Observações factuais sobre fronteiras que hoje funcionam por serem simulação, mas que valem uma decisão explícita antes de qualquer um desses caminhos virar produção.

01

Admin-front fura o admin-back para executar

A aba Execução chama localhost:8083 (ms-espec-registry) direto do navegador, sem token de sessão do admin. Funciona porque é simulação, mas contraria a fronteira dos requisitos ("o Admin Portal conhece apenas a API de publicação do runtime"). Vale decidir se isso continua sendo um atalho de debug documentado, ou se a aba de Execução passa a ser só leitura via admin-back.

02

Dois ciclos de vida de instância duplicados

ms-espec-registry (SimulationController) e ms-journey (JourneyController + JourneyStepResolver) implementam start/complete/current-step contra o mesmo Camunda de forma independente. Já compartilham o FormSpecController para specs — se o ms-journey vira o único runtime de verdade, vale avaliar extrair a resolução de passo para não deixar a lógica divergir entre os dois.

03

Dashboard do admin-back fala direto com o Camunda

RuntimeEngineMonitoringAdapter chama engine-rest:8080 cru para instâncias/incidentes, enquanto a publicação passa pelo ms-transform-publication. São duas portas de entrada diferentes para o mesmo runtime — se o objetivo é ter uma única fachada de runtime, o monitoramento operacional é candidato a migrar para trás dela também.

04

ms-espec-registry ainda acumula 3 responsabilidades sem relação

Simulador de execução, registry de specs de formulário e proxy de teste de conexão do Integration Catalog vivem no mesmo serviço (a bridge Kafka automática saiu, foi pro ms-runtime-camunda). Razoável numa fase de simulação; se o registry de specs for promovido, ele é conceitualmente parte do domínio Forms/Modeler do admin, não do runtime — vale separar por responsabilidade nesse momento.

05

Jornada já publicada antes desta mudança não tem o type do outputMapping

O worker Kafka do ms-runtime-camunda lê outputMapping.<name>.type direto do BPMN implantado (BpmnTransformer só passou a gravar isso agora) — uma jornada com RECEIVE_TASK/MESSAGE_START_EVENT Kafka publicada antes dessa mudança não tem esse input parameter e cai no default string ao extrair a variável de uma mensagem recebida. Republicar a jornada resolve; vale conferir se alguma das jornadas de teste existentes usa number/boolean/date nesse cenário específico.

06

Event Hubs/Service Bus continuam sem worker

O worker embutido no ms-runtime-camunda só trata connectorType=KAFKA — um SERVICE_TASK/RECEIVE_TASK/MESSAGE_START_EVENT com Event Hubs ou Service Bus (habilitados no catálogo de conectores, REQ do Journey Modeler) continua virando External Task sem ninguém para completar, mesma situação que o Kafka tinha antes desta mudança.
